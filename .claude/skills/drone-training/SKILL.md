# Skill: навігація по drone-training

Ти працюєш у проєкті **drone-training** — навчальний симулятор FPV та великих БПЛА
(як Liftoff) з опційним ML для виявлення й «ураження» **віртуальних** цілей.
Цей скіл — твоя карта. Прочитай його повністю перш ніж редагувати код.

## 0. Область і етика (прочитай першим)
Це **симулятор/гра**. Усі цілі — віртуальні об'єкти в сцені Panda3D. «Ураження» =
подія в симуляції (зближення з маркером у межах порогу) + очки. Тут **немає**
реальної зброї, апаратного наведення чи інтерфейсів до реального обладнання.
Не додавай коду, що керує фізичним залізом або зброєю. Якщо задача просить вийти
за межі симуляції в реальний світ — зупинись і спитай користувача.

## 2. Де що лежить (швидка мапа)
```

  render/     ← Panda3D-рушій: сцена, FPV-камера, PBR, HUD,
              detection_overlay.py (PIP+bbox), attach_main_camera (фаза 2,5)
              models.py — процедурні 3D-меші (дерево/техніка/артилерія/паркан/
              окоп/дорога/будівля, справжній Geom-API, не картки); effects.py —
              ExplosionEffect (спалах+дим+Bullet-уламки) (доп. фаза "реальні моделі");
              sky.py — купол неба+сонце+туман (доп. фаза "жива графіка");
              materials.py — PBR-пресети (roughness/metallic, Material-об'єкти);

              тут; чекнуті в репо заради відтворюваності (доп. фаза "графіка 2.0")
  vehicles/   ← моделі апаратів + польотні контролери         (фази 1,2,3)
  input/      ← клавіатура, геймпад PS, RL-агент як джерело    (фази 2,7)
  world/      ← сцени (configs/ і assets/scenes/), цілі/ворота  (фаза 4)
  scenarios/  ← місії: gate_race, patrol, strike_range, event_log (фаза 4)
  ml/detection ← YOLO: recorder→train→detector→eval             (фаза 5)
  ml/rl/      ← DroneEnv(gymnasium), rewards, PPO train/eval     (фаза 6)
  ml/data/    ← projection.py, scripted_flight.py, yolo_format.py,
              recorder.py — синтетичні датасети з симу          (фаза 5)
  ui/         ← CLI app.py, results.py (текстовий екран результатів)
  gui/        ← PySide6-лаунчер: scan/process/calibration_store (чисті
              функції) + main_window.py (Qt) + launcher.py — запускає
              dronesim.app ОКРЕМИМ процесом, ніколи не імпортує Panda3D/torch
              ("справжній Liftoff")
  utils/      ← pid, математика, логування
configs/      ← ВСІ параметри (YAML). Магічних чисел у коді немає.
tests/        ← pytest на кожен модуль
scripts/      ← headless-утиліти (hover_test, demo_autonomous)
```

## 3. Непорушні правила проєкту
1. **Контракти в `core/contracts.py` — священні.** `ControlCommand`,
   `VehicleState`, `CameraFrame`, `Detection` — спільна мова всіх модулів.
   Хочеш змінити поле — спочатку онови контракт, знайди всіх споживачів
   (`grep`), онови їх, онови тести. Ніколи не форкай контракт «локально».
2. **Джерело керування взаємозамінне.** Людина (геймпад) і ML-агент видають
   один і той самий `ControlCommand`. Не роби окремих гілок «if human/if ai»
   у фізиці чи контролерах — вони не мають знати, звідки команда.
3. **Ніяких магічних чисел.** Маса, коефіцієнти тяги, PID-гейни, deadzone,
   пороги — усе в `configs/*.yaml`, читається через `core/config.py`.
4. **Детермінізм.** Будь-яка випадковість — через переданий `seed`. Це критично
   для відтворюваності ML.
5. **Кожен модуль — тест + докстрінг-контракт.** Без тесту фаза не закрита.
6. **Не змішуй шари.** ML споживає `CameraFrame`/`VehicleState`, повертає
   `ControlCommand`. Рендер не рахує фізику. Введення не знає про Panda3D/Bullet.

## 5. Типові пастки (і як не влипнути)
- **Немає геймпада для тесту.** Клавіатуру доводь інтерактивно; геймпад —
  юніт-тестом на мапінг осей із фейковими pygame-подіями. Не блокуйся на цьому.
- **Рендер на headless/у тестах.** Для тестів і збору даних запускай Panda3D
  offscreen (`window-type offscreen`, є GSG для рендеру, немає вікна ОС). Вікно з картинкою — лише для
  інтерактивного польоту. Фізика (Bullet) працює без вікна.
- **Нестабільний PID.** Гейни — в конфіг; тюнинг ітеративно на `scripts/hover_test.py`.
  Спершу rate-loop (Acro), потім надбудовуй angle/position.
- **`Quat.getW()` у Panda3D завжди повертає 0** (виявлено емпірично у фазі 3).
  Правильний акцесор скалярної частини кватерніона — **`getR()`**. Якщо десь
  результат із `Quat`/`LVecBase*` виглядає підозріло нульовим — перевір це першим.
- **Не переноси знакову конвенцію між різними фізичними залежностями без
  окремої емпіричної перевірки.** У фазі 3 rate-мікшер (roll↔ang_vel) і
  tilt→прискорення (roll↔world-Y) виявились АСИМЕТРИЧНИМИ за знаком, хоча
  pitch↔X — ні. "Здається симетричним" ≠ "є симетричним"; прожени реальний
  тест, подивись напрямок руху, тоді фіксуй знак.
- **"Вперед" для тіла апарата — це ЛОКАЛЬНА +X**, не +Y (Panda3D-камера за
  замовчуванням дивиться вздовж своєї +Y — саме тому FPV-камера монтується з
  `setHpr(-90,0,0)`, render/camera.py). Використовуй
  `utils/math3d.py::vehicle_forward_world` для напрямку носа в світових
  координатах (геометрія цілей/влучань), не вигадуй наново.
- **`NodePath.lookAt()` + подальша ручна зміна Euler-кутів (`setH(getH()-90)`)
  ЛАМАЄТЬСЯ, якщо є ненульовий pitch** (Euler-компоненти не компонуються так
  просто). Виявлено у фазі 5 (`ml/data/recorder.py`): якщо потрібен інший
  "forward"-конвент, ніж нативний Panda3D +Y — передай `mount_hpr=(0,0,0)` у
  `FPVCamera` і використовуй `lookAt()` напряму, а не крути результат вручну.
- **КРИТИЧНО (Windows): `torch`/`ultralytics` МАЄ бути імпортований (і
  бажано інстанційований) ДО Panda3D в одному процесі.** Інакше нативні DLL
  конфліктують: `torch` падає з `OSError: DLL init routine failed` (не
  Panda3D!), якщо Panda3D вже завантажений раніше в цьому ж процесі. Порядок
  ІМПОРТУ/СТВОРЕННЯ ОБ'ЄКТА важливий, порядок ВИКОРИСТАННЯ — ні. Тому:
  `tests/conftest.py` імпортує `torch` першим рядком (перед `render.engine`);
  `app.py::build_fly_session` створює `Detector(...)` ДО імпорту `Engine`,
  якщо задано `--detector`. Якщо додаєш новий шлях, що змішує ML і рендер —
  дотримуйся цього порядку, інакше отримаєш незрозумілий DLL-crash, що
  виглядає як зламаний torch, а насправді — конфлікт порядку імпорту.
- **Правило вище стосується й ТРАНЗИТИВНИХ імпортів, не лише твоїх власних
  top-level.** Виявлено у фазі 7: `input/rl_agent.py` імпортував
  `make_relative_obs` з `ml/rl/env.py` — а `env.py` сам тягне
  `physics.world`/Panda3D для класу `DroneEnv`. Сам ІМПОРТ (до виклику
  `RLAgentSource.__init__`, де лінивий `from stable_baselines3 import PPO`)
  уже ламав torch. Виправлено виділенням Panda3D-вільного
  `ml/rl/observations.py`. Перш ніж імпортувати функцію з важкого модуля —
  перевір, що ІМПОРТУЄ сам цей модуль.
- **Той самий DLL-порядок ламається і в тестових inline-скриптах, якщо
  імпортуєш `panda3d.core` (напр. заради `ClockObject` для детермінованого
  кроку фізики) РАНІШЕ за `build_fly_session`.** Виявлено в доп. фазі
  "справжній Liftoff": тест з `from panda3d.core import ClockObject` на
  початку скрипта, ПЕРЕД `from dronesim.app import build_fly_session`,
  ламав torch, хоча сам тест про autopilot/RL, не про рендер. Імпортуй
  `ClockObject` (чи будь-що з `panda3d.core`) ПІСЛЯ виклику
  `build_fly_session(...)`, якщо сесія створює `RLAgentSource`/`Detector`.
- **"Реалістичні" числа з реальної документації (BetaFlight rates, PID
  тощо) можуть бути ОБ'ЄКТИВНО правильними й СУБ'ЄКТИВНО непридатними для
  конкретного способу вводу.** "Гонкові" 670°/с (типові для реальних FPV-
  пілотів з аналоговим стіком) відчувались як миттєва втрата контролю на
  клавіатурі (грубий цифровий "віртуальний стік", без тонких корекцій) —
  реальний фідбек користувача "вилітаю як ракета" (доп. фаза "справжній
  Liftoff"). Урок: після звірки формули з джерелом ОБОВ'ЯЗКОВО ще й
  перевір емпірично, як воно ВІДЧУВАЄТЬСЯ для цільового способу вводу —
  не лише що математика правильна.
- **PID-гейни НЕ переносяться між апаратами з різною інерцією "на око"
  (напр. "прискорити" гейни quad_large для легшого fpv_5inch).** Перша
  спроба Angle-режиму для fpv_5inch (kp=6.0/kd=0.05, "логічно швидше" за
  quad_large) дала перерегулювання +19° понад ціль і коливання ±23° після
  відпускання стіка — недостатнє демпфування для 13x легшого апарата.
  Завжди перевіряй empiричним `kp`/`kd`-перебором (headless-скрипт, як
  `scripts/hover_test.py`), не екстраполюй з іншого апарата.
- **RL-агент (фаза 6/7) навчений НАВІГАЦІЇ вже в повітрі, НЕ злету з
  землі** — `ml/rl_strike.yaml::start_altitude_range` завжди відносно
  висоти цілі, ніколи біля землі. Запуск автономного режиму з висоти
  людського ручного зльоту (1м) — ПОЗА розподілом навчання: апарат встигає
  торкнутися землі до стабілізації Pos-hold і "застрягає" там (реальний баг,
  доп. фаза поліш). `app.py::build_fly_session` тепер стартує на 3м, коли
  `start_autonomous=True`. Урок ширший: "не падає за N кроків" (типовий
  смоук-тест) НЕ перевіряє, що апарат РЕАЛЬНО виконує задачу — окремо
  перевіряй кінцевий стан (висота/позиція) після ДОСТАТНЬОЇ кількості кроків,
  не лише відсутність винятку.
- **Інша, не пов'язана пастка на Windows: `subprocess.run(..., env={...})` з
  ЧАСТКОВИМ словником ЛАМАЄ torch у дочірньому процесі.** `env=` ПОВНІСТЮ
  замінює середовище (не додає), лишаючи дочірній процес без
  `PATH`/`SYSTEMROOT` — і torch падає з `OSError: [WinError 10106]` углибині
  власного імпорту (`asyncio.windows_events` → `_overlapped`), СОВСІМ інша
  помилка за DLL-порядок Panda3D вище. Завжди `env={**os.environ,
  "PYTHONPATH": ...}` у subprocess-тестах, що завантажують torch/ultralytics.
- **Сценарії (`scenarios/*.py`) мають ФІКСОВАНІ позиції цілей/воріт із
  YAML-конфігу — їхній `reset(seed=...)` НЕ рандомізує розкладку** (на
  відміну від `DroneEnv`, що рандомізує ціль щоразу). Якщо пишеш
  multi-seed оцінку/тест поверх РЕАЛЬНОГО сценарію (не `DroneEnv`) з
  детермінованою політикою — різні `seed` без ДОДАТКОВОГО власного джерела
  варіації (напр. рандомізований старт апарата) дадуть БАЙТ-В-БАЙТ
  ІДЕНТИЧНИЙ результат для кожного "епізоду" (виявлено у фазі 7,
  `scripts/eval_autonomous.py`) — фіктивна статистика, що виглядає
  правдоподібно, поки не звіриш episode-by-episode дані.
- **`DirectionalLight.setShadowCaster(True, ...)` МОВЧКИ не рендерить тіні,
  якщо вузол світла не має явної ПОЗИЦІЇ.** Напрямок задає лише `setHpr` —
  цього досить для звичайного освітлення, АЛЕ тіньова ортографічна камера
  Panda3D прив'язана до фактичної позиції вузла; без `setPos` вузол лишається
  в `(0,0,0)`, near/far лінзи обрізає сцену, і тіней просто немає — без жодної
  помилки чи попередження (виявлено у доп. фазі поліш, `render/engine.py`,
  через піксельний аналіз скріншотів, не через лог). Фікс:
  `sun_np.setPos(sun_np, 0, -shadow_extent_m, 0)` одразу після `setHpr`
  (зсув "назад" уздовж УЖЕ повернутої орієнтації). Урок ширший: "API не
  кинув виняток" ≠ "візуальна фіча працює" — перевіряй реальний скріншот.
- **Повний `pytest -q` іноді падає на subprocess-тесті з НАТИВНИМ кодом
  виходу (напр. `3221225477` / `0xC0000005`, Windows `STATUS_ACCESS_VIOLATION`),
  а не звичайним Python-traceback.** Виявлено у доп. фазі поліш: багато
  subprocess-тестів поспіль створюють ВЛАСНИЙ offscreen Panda3D `Engine`
  кожен — під навантаженням повного прогону це іноді тисне на GPU-драйвер
  (AMD, Windows) і краше один випадковий тест. НЕ вважай це регресією одразу
  — спершу перевір відтворюваність: той самий виклик окремо (кілька разів),
  весь тестовий файл окремо, повний прогін ще раз. Якщо не відтворюється
  ізольовано — це середовищна нестабільність, не баг коду (docs/DECISIONS.md).
- **Не будуй бібліотеку 3D-форм (циліндри/конуси/складені моделі) наосліп —
  перевір ОДИН тестовий меш скріншотом перед тим, як писати решту.**
  Доп. фаза "реальні моделі": до `render/models.py` спершу перевірено
  ізольований циліндр (нормалі/освітлення коректні на вигнутій поверхні),
  і ОКРЕМО — компонування вежі техніки через кілька ракурсів (top-down,
  збоку), бо `barrel.setP(90)` "логічно" мав вказувати вперед, а насправді
  вказував убік; правильна комбінація (`setHpr(90,90,0)`) знайдена лише
  перебором на маркованому тестовому циліндрі. Так само нахил ствола
  артилерії, що ЗДАВАВСЯ вертикальним на одному ракурсі (Y-вісь камери),
  виявився коректним при перевірці з перпендикулярного ракурсу (X-вісь) —
  ракурсне скорочення оманливе, перевіряй з кількох камер, не з однієї.
- **Нові моделі сценерії (дерево/техніка/паркан тощо), що будуються з
  ЛОКАЛЬНИМ origin=0 як БАЗОЮ, потребують Z-зсуву відносно
  obstacle-конвенції `pos.z == half_extents[2]` (центр фізичної коробки).**
  `render/models.py::attach_scenery_visual` застосовує `model.setZ(-hz)`
  для будь-якого `kind != "box"`; забудеш — об'єкт візуально "плаває" над
  землею, хоча фізична коробка стоїть правильно.
- **`NodePath.isEmpty()` після `removeNode()` — природний, вже готовий
  сигнал "об'єкт видалено", придатний як ідемпотентний тригер (не заводь
  окремий `set()` для відстеження "вже оброблено").** Використано в
  `app.py::_sync_target_markers` для тригера `ExplosionEffect` рівно раз
  на ціль (доп. фаза "реальні моделі").
- **`OnscreenText`/2D-елемент: координати ЗАЛЕЖАТЬ від батька-якоря.**
  `aspect2d` — центр-origin (x: -aspect..+aspect, y: -1..+1); `a2dTopLeft` —
  origin у лівому верхньому куті (x росте ВПРАВО від 0, y ВНИЗ у ВІД'ЄМНІ);
  аналогічно `a2dBottomRight` тощо. Координати `aspect2d` під батьком
  `a2dTopLeft` виносять елемент ПОЗА екран — саме так HUD став невидимий
  ("немає інтерфейсу", доп. фаза "жива графіка"). Обирай координати ПІД
  конкретний якір і перевіряй скріншотом головного вікна, не лише "тест не
  падає" (тест бачив текст у вузлі, але той був за межами кадру).
- **Скайбокс/далека геометрія вимагає піднятої far-площини камери.** Купол
  неба радіусом 1400м обрізало стандартною far (~1000м) — небо не
  рендерилось. `engine.camLens.setFar(4000)` після додавання неба. Також:
  небо має бути в біні "background" з вимкненими depth-write/освітленням/
  ШЕЙДЕРОМ PBR і **туманом** (`setFogOff`) — інакше глобальний туман кольору
  горизонту "з'їдає" все небо на відстані купола (`render/sky.py`).
- **Ціль-модель ЗАВЖДИ на землі (`base_z=0`), а хіт-сфера на висоті —
  свідомий декуплінг.** Техніка strike_range малюється на землі
  (`_sync_target_markers` ставить `(x, y, 0)` для vehicle/artillery), а
  `check_hit` працює з `position_at` (центр сфери на config-z) — влучаєш,
  пролітаючи над наземним силуетом. НЕ роби `base_z = max(0, z - radius)`:
  рівні з високими цілями й малим радіусом (sniper z6/r1) лишають танк у
  повітрі. Хіт-центр НЕ опускай до z=0: автономна RL-політика навчена на
  цілях у повітрі (ml/rl_strike), z=0 змінив би задачу й апарат осідав би в
  землю (регрес, test_app_autonomous.py). Зміна висот цілей впливає й на
  автономний режим, не лише на візуал.
- **`attach_scenery_visual` застосовує СПІЛЬНЕ грунтування `setZ(-hz)` до всіх
  kind — воно ПЕРЕЗАПИСУЄ будь-який локальний Z, заданий у білдері моделі.**
  Дорога (плаский декаль) глючила об землю (z-fighting), бо її внутрішній
  `setZ(0.06)` затирався грунтуванням до z=0; вертикальний зсув треба задавати
  В ДИСПЕТЧЕРІ (`setZ(-hz + 0.06)` для road) + `setDepthOffset`, не в білдері
  (доп. фаза "жива графіка").
- **Небо/хмари-білборди: гаси альфу текстури до 0 по краях (віньєтка).**
  Без цього видно прямокутний шов картки в небі (хмара — гаусові плями, що
  на краю картки не досягають 0). `render/sky.py::_make_cloud_texture`
  множить альфу на крайову віньєтку. Далекі пагорби (`scatter_hills`) —
  візуальні, ЗА межею поля, фізику польоту не чіпають (політ над плоскою
  землею); god rays НЕ реалізовано (потребують пост-процесингу).
- **Доп. фаза "реалізм фізики": усі 8 нових ефектів (мотор-лаг/батарея/
  екранний ефект/квадратичний опір/feed-forward/airmode/шум гіроскопа-
  латентність/турбулентний вітер) вмикаються ЛИШЕ за наявності поля в
  `configs/vehicles/*.yaml` (`cfg.get("поле", 0.0)`).** Відсутність поля =
  стара поведінка 1:1 — це дозволило додати всі вісім без зміни сигнатур
  викликів у десятках існуючих тестів. `Vehicle.apply_motor_commands(thrusts,
  dt=None)` — НОВИЙ опційний `dt`; `dt=None` вимикає інерцію моторів/батарею
  (миттєвий відгук, як і раніше) — виклики БЕЗ `dt` (старі тести) лишаються
  коректними. Якщо додаєш ЩЕ один опційний фізичний ефект — той самий патерн.
- **Зміна ФОРМУЛИ похідної в PID (напр. похідна-від-виміру замість
  похідної-від-похибки) міняє демпфування ВСЬОГО каскаду, навіть якщо
  зовнішній контур (Angle/AltHold/PosHold) не чіпали.** Виявлено емпірично:
  перехід rate-loop (`vehicles/controllers/rate_loop.py`) на
  `measurement=body_rate[i]` (уникає derivative-kick на стрибках стіка)
  ослабив демпфування каскаду Angle fpv_5inch — залишковий крен після
  відпускання стіка зріс з ~0.75° до ~3.1° (поріг тесту — 3.0°). Виправлено
  ПЕРЕТЮНИНГОМ kd (headless sweep), не поверненням старої формули. Урок:
  ніколи не вважай зміну внутрішнього контуру "ізольованою" без емпіричної
  перевірки каскаду в цілому (`pytest tests/test_angle_controller.py` тощо).
- **Тест "стара vs нова поведінка" МАЄ явно задавати ОБИДВА стани, якщо
  змінюваний параметр колись стане production-дефолтом.** Тест airmode
  порівнював два апарати, один з яких покладався на ДЕФОЛТ конфігу (не
  задавав `airmode` явно) — коли `configs/vehicles/*.yaml` отримали
  `airmode: true` за замовчуванням, "контрольний" апарат теж став "з
  airmode", і порівняння почало фейлитись (`spread_air == spread_plain`).
  Завжди явно `cfg.airmode = False` в контрольній гілці такого тесту.
- **`rotor_radius_m<=0` (екранний ефект не налаштовано) МАЄ повертати
  нейтральний множник 1.0, НЕ максимальний буст.** Перша версія
  `aerodynamics.ground_effect_factor` мала цю умову навпаки (той самий клас
  пастки, що й `attach_scenery_visual`/z-offset раніше — "вимкнено" й
  "гранична умова" — це РІЗНІ гілки, легко переплутати знаком).
- **Без `NodePath.setMaterial()` Panda3D підставляє ГЛОБАЛЬНИЙ дефолт
  (`roughness=1.0`, повністю матовий, `metallic=0.0`) для БУДЬ-ЯКОГО
  об'єкта.** `setColor()` (вершинний колір) впливає лише на ВІДТІНОК, не на
  "блискучість" — без явного `Material` метал/гума/земля виглядають
  ОДНАКОВО матовими. `render/materials.py` тримає `baseColor=(1,1,1,1)`
  (нейтральний) у кожному пресеті, щоб не подвоїти тонування з наявним
  `setColor()` (`simplepbr.frag` рахує `Material.baseColor * v_color`).
- **`NodePath.flattenStrong()` ВТРАЧАЄ `TransparencyAttrib` (і, ймовірно,
  інші render-атрибути), якщо його встановлено на вузлі-ОБГОРТЦІ, яка
  зникає при флатенізації — застосовуй такі атрибути на НАЙГЛИБШОМУ
  листковому вузлі геометрії.** Виявлено на траві (`build_grass_tuft`,
  `scatter_ground_cover` зводить сотні пучків в один вузол): transparency
  на обгортці `tuft` губилась після flatten, трава рендерилась суцільними
  прямокутниками замість альфа-вирізаного силуету. Перевіряй через
  `node.getAttrib(TransparencyAttrib)` ДО/ПІСЛЯ flatten, якщо щось виглядає
  не так після зведення сотень об'єктів в один вузол.
- **UV-мапування текстури на `CardMaker`-картку НЕ інтуїтивне: рядок
  зображення y=0 рендериться на ВЕРХНЬОМУ краю картки (V=1), не на
  нижньому.** Перевір емпірично (тестова картка з різнокольоровими
  половинками) перш ніж писати текстуру з вертикальною асиметрією
  (напр. "широка база -> вузький кінчик" для трави/дерев) — і НЕ
  використовуй камеру з `lookAt()` для діагностичних скріншотів такої
  геометрії: `lookAt()` іноді дає неочікуваний ROLL/up-вектор і може
  ВІЗУАЛЬНО перевернути результат, хоча дані коректні (виявлено на траві —
  `lookAt`-камера показувала перевернутий силует, `setHpr`-камера з тим
  самим кодом — правильний).
- **Blender -> glTF -> Panda3D (`gltf2bam`): вісь "вперед" МОЖЕ зберегтись
  без додаткової корекції, якщо модель побудована з носом на Blender +X**
  (Z-up/-Y-forward -> glTF Y-up/-Z-forward -> Panda3D Z-up конвертація,
  підтверджено ЕМПІРИЧНО скріншотами з кількох камер, не виведено
  теоретично) — але це НЕ гарантія для БУДЬ-ЯКОЇ моделі; перевіряй кожен
  новий Blender-ассет так само (top-down + вигляд збоку).
- **Нова офлайн-камера (мaска god rays, окремі буфери тощо) успадковує
  СПІЛЬНИЙ `Lens`-об'єкт, якщо передати `lens=base.camLens` — включно з
  дефолтним ВУЗЬКИМ FOV (~39°) Panda3D, якщо ГОЛОВНА камера тестового
  скрипта не викликала `setFov`.** Симптом: додаткова камера "нічого не
  бачить" (чорний буфер), хоча геометрія/позиції коректні — перевіряй
  `lens.getFov()` перш ніж підозрювати логіку розміщення об'єктів.
- **КРИТИЧНО: ShowBase у ВІКОННОМУ режимі вмикає trackball-мишу, яка
  ЩОКАДРУ перезаписує трансформ `base.camera` — ручне позиціонування
  головної камери МОВЧКИ ігнорується.** В offscreen миші немає -> трекбол
  не створюється -> headless-тести/скріншоти виглядають правильно, а
  реальна гра — ні (камера застрягає в центрі корпусу, дивиться +Y замість
  +X носа; "весь екран жовтий" — корпус зсередини). `Engine.__init__`
  викликає `disableMouse()` — НЕ прибирай. Урок ширший: headless-перевірки
  НЕ покривають window-only поведінку ShowBase; багрепорт "у грі не так,
  як на скріншотах" -> відтворюй у РЕАЛЬНОМУ вікні; дамп
  GraphicsOutput->DisplayRegion->Camera->світовий трансформ показує, яка
  камера насправді малює в вікно (docs/DECISIONS.md 2026-07-20).
- **Panda3D дефолтний near-plane лінзи (1.0м) обрізає ЗЕМЛЮ під
  низьколетючим апаратом** ("камера бачить крізь землю", доп. фаза "графіка
  3.0") — для FPV-камери, змонтованої в сантиметрах від корпусу,
  ОБОВ'ЯЗКОВО `lens.setNear(~0.03)` (render/camera.py::DEFAULT_NEAR_M).
- **Пара протилежних граней коробки/стін через CardMaker+setHpr вимагає
  РІЗНИХ headings (типово 180° різниці)** — CardMaker має ОДИН фіксований
  дефолтний normal (0,-1,0); однаковий heading для обох граней пари дає
  нормаль ВСЕРЕДИНУ на одній із них. `setTwoSided` ховає "грань невидима",
  але освітлення лишається неправильним ("не видно, звідки сонце" — реальний
  баг у `_BOX_FACES` і стінах будівлі, доп. фаза "графіка 3.0"). Перевіряй
  `getRelativeVector(node, Vec3(0,-1,0))` на кожній грані (регрес-тести
  test_visuals.py/test_models.py).
- **`flattenStrong()` НЕ лінійний за кількістю вузлів (~O(n²)): тисячі
  об'єктів = десятки секунд.** Для тисяч однотипних об'єктів будуй ОДИН
  Geom. Для ДЕСЯТКІВ ТИСЯЧ (килим трави ~200k стебел) навіть
  Python-цикл `GeomVertexWriter` завеликий — рахуй ВСІ вершини numpy й
  блитай одним `modifyArray(0).modifyHandle().copySubdataFrom(bytes)` +
  `uncleanSetNumRows` (`render/models.py::_build_blade_field_mesh`): десятки
  мс. **Пастка блиту:** формат з color (`V3n3c4t2`) зберігає color як 4
  УПАКОВАНІ БАЙТИ (stride 36), НЕ 4 float32 — плоский float-блит зсуває
  вершини ("смуги через екран"); використовуй структурований numpy-dtype і
  перевіряй `getColumn().getTotalBytes()`. Масова рослинність — alpha-TEST
  (`MBinary`), не alpha-BLEND (`MAlpha`, вимагає сортування щокадру).
- **Трава/рослинність через density map + jittered grid** (стандарт ігор,
  `_grass_density`/`scatter_ground_cover`): рівномірна сітка кандидатів +
  функція густоти (шум + галявини-кола smoothstep→0) вирішує, які проростуть.
  Текстура — КЛУМП тонких стеблин із проміжками, не одне суцільне "листя"
  (інакше картка = конус, "поле шпилів").
- **Рельєф землі — heightmap на основі Вороного (`_voronoi_cells` →
  `_terrain_height_grid` → `_terrain_height`), не окремі "бульбашки".**
  Насінини з випадковим `kind` ("hill"/"ravine"/"flat") → растеризація
  найближчої насінини на грубу сітку (класичне розбиття Вороного) → box-blur
  розмиває гострі межі полігонів → радіальне згасання на краю сітки →
  `_bilinear_sample` для довільних точок запиту. Це свідома "основа для
  майбутнього": нові kind (річки/гори/посадки) — розширення ЛИШЕ
  `_voronoi_cells`, решта конвеєра незмінна. Стара версія (окремі кругові
  "форми" `_terrain_features`) і ще старіша (`build_hill`/`scatter_hills` —
  декоративні купола-"бульбашки" на горизонті) — ОБИДВІ видалені повністю
  (реальний фідбек: перша "лиш трохи нерівна", друга "величезні бульбашки").
  Плоско в робочій зоні (`flat_radius`, рахується ДИНАМІЧНО з фактичних
  obstacle/target/gate у `app.py`, не хардкод) → окремі купола/западини
  розкидані далі — між ними РЕАЛЬНО пласко (0), не проміжне значення. Кожна
  форма обмежена своїм радіусом, тож не треба явного "згасання до
  горизонту" — вплив завжди лишається задовго до декоративних пагорбів
  (`scatter_hills`, стоять на z=0 за 150м); якби рельєф був СУЦІЛЬНИМ
  плато/кільцем без обмеженого радіуса впливу, він "затопив" би їхню базу.
  `_terrain_flat_spot` знаходить дійсно рівну пляму серед форм (перевіряє
  усі кути кандидата-квадрата) — для розміщення контенту (пшениця), що
  вимагає рівної землі.
- **Функція, що перебудовує важку структуру (сітку/шум) з нуля на КОЖЕН
  виклик, МАЄ бути `@functools.lru_cache`, якщо викликається багато разів
  з тими самими аргументами в межах сесії** (`_terrain_height_grid`) — і
  НІКОЛИ не клич її "раз на елемент" у циклі (кущ/дерево/точка), навіть
  якщо сам виклик "здається дешевим"; збирай усі точки й рахуй ОДНИМ
  пакетним викликом ПІСЛЯ циклу. Знайдено профілюванням: 90 кущів × 30мс
  перебудови сітки = ~3с зайвих на одну сесію.
- **`scipy.spatial.Delaunay` коштує ~2с на ПЕРШИЙ імпорт у процесі** —
  помітно на тлі бюджету тестів, що будують сесію в дочірньому процесі з
  таймаутом. Якщо потрібне лише наближення сусідства Вороного (не точна
  тріангуляція) — растеризація (груба сітка, найближча насінина на піксель,
  різні сусідні пікселі → сусідні насінини, `_voronoi_adjacency`) не
  потребує важкої залежності.
- **Будь-яка процедурна лінія/розсипка об'єктів уздовж відрізка змінної
  довжини (паркан, лісосмуга) МАЄ мати верхній кап на к-сть елементів і
  `flattenStrong()` на результат** — інакше рідкісний "довгий" відрізок
  (напр. витягнуте поле) дає сотні нефлетнутих NodePath, що гальмують
  cull ЩОКАДРУ, не лише час побудови (той самий прийом, що вже
  використовує `scatter_ground_cover` для кущів).
- **Перш ніж вважати повільність тесту "регресією" — перепроганяй його
  ІЗОЛЬОВАНО.** Кілька профілюючих `Engine()`-скриптів поспіль в одному
  сеансі можуть лишити побічне навантаження на систему/GPU-драйвер, через
  яке СУСІДНІЙ тест з коротким таймаутом (тут — 60с підпроцес) провалиться
  без жодних змін коду. Завжди перевіряй у спокійному стані перед тим, як
  латати "продуктивність".
- **Спільне процедурне поле, яке читають ДВА РІЗНІ виклики (тут: колір
  землі й колір/висота трави з `_terrain_dryness`), МАЄ нормалізуватись
  РАЗ на самій сітці шуму (до семплінгу), не на вибірці точок кожного
  виклику, і семплитись з ОДНАКОВИМ фіксованим extent.** Інакше однакова
  world-координата дає різний результат залежно від того, ХТО питає (мала
  локальна вибірка нормалізується інакше, ніж уся сітка мешу) — реальний
  баг, знайдений тут: трава й земля не збігались кольором. Колірний
  градієнт (зелене↔жовте) потребує КОНТРАСТНОГО ремапу значень
  (`(d-0.5)*k+0.5`) — сирий нормалізований шум дає суцільний "оливковий"
  блендінг без чітких плям; перевіряй кольорове поле окремим top-down
  numpy-рендером (дешевше й точніше за 3D-скріншот із туманом/освітленням).
- **Рослинність із вертикальних карток освітлюй UP-нормалями (0,0,1), не
  геометричними нормалями карток** — інакше 1-2 з 3 карток кожного пучка
  дивляться ВІД сонця й рендеряться майже чорними. Стандартний трюк ігрової
  трави: нормаль як у землі під рослиною -> зливається в природний килим.
  Для CardMaker-карток нормалі патчаться `GeomVertexRewriter` після
  `generate()` (build_bush).
- **Наближений розрахунок нормалей НЕ переноситься між формами з різною
  монотонністю радіуса**: прийом build_hill (купол, радіус лише спадає)
  дав ПОВНІСТЮ ЧОРНИЙ камінь на повній кулі (радіус росте, потім спадає) —
  для сфер тільки аналітична нормаль (нормована позиція вершини);
  приплюснутість — через `setScale` на вузлі (Panda3D сам коректно
  перераховує normal-матрицю), не ручним псуванням вершин.
- **RL не вчиться.** Починай із «телепорт-obs» (ідеальна відносна поза цілі),
  доведи, що агент учиться, і лише потім підключай зашумлені детекції YOLO.
- **Дрейф контрактів.** Перед змінами в `contracts.py` — `grep` по всьому `src/`.
- **Важкі ML-тести позначай `@pytest.mark.slow`** (зареєстровано в
  `pyproject.toml`). `pytest -q` (без фільтра) ганяє все, включно з ними;
  `pytest -q -m "not slow"` — лише швидкі (секунди, не хвилини).
